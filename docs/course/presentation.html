Key Decision: Why Kinesis in the Middle?

IoT rules can invoke Lambda directly — Kinesis is the one service I could have left out.

What it buys

  • Ordering partition key = shipment → one truck's pings stay in order
  • Replay 24 h retention — a fixed Lambda re-processes what a buggy one dropped
  • Buffer bursts (30-day backfill: ~23k messages) are smoothed, Lambda reads in batches of 100
  • Fan-out analytics / alerting consumers can read the same stream later

What it costs

Money
1 provisioned shard ≈ $0.015 / h ≈ $0.36 / day, even when idle — the largest line item of the PoC.
Mitigation: cdk destroy after every session. On-Demand mode has a higher base price — wrong choice at 40 trucks.
Capacity (measured)
Avg. message 1.76 KB → 1 MB/s per shard ≈ 17,000 trucks at 30 s reporting.
Scaling = add shards; Lambda gets one concurrent consumer per shard.
Measured run: SQS instead
The AWS Free plan has no Kinesis, so the stack is switchable: -c ingest=sqs puts a standard SQS queue in its place.
Lost: ordering and replay. Ordering doesn't matter, because the seq check makes the result order-independent (tested). Replay is the real loss.

process_event: Exactly-Once Effect on At-Least-Once Delivery

MQTT QoS 1 and Kinesis retries both deliver duplicates; network jitter reorders. Every message carries a per-shipment seq — DynamoDB only accepts newer ones:

table.update_item(
  Key={"shipmentId": msg["shipmentId"]},
  UpdateExpression="SET " + ", ".join(sets),
  ConditionExpression=
    "attribute_not_exists(seq) OR seq < :newseq",
  ...
)
# ConditionalCheckFailed → duplicate / stale: skip

History rows use a sort key derived from the event itself → a replay overwrites instead of duplicating.

Per record, in order

  • Validate ID format, seq, status, coordinates → invalid = DLQ, never retried
  • History milestones (departed, border, customs, POD…) → ShipmentEvents
  • KPI keep the ETA predicted at half-way (lowest seq wins — order-independent)
  • State conditional upsert + ingestLatencyMs stamp
  • Errors transient → partial batch failure, only that record onward is retried

Operator-owned fields (delay flag) are never overwritten by telemetry.

Honest limitation

Where it runs: on the telematics unit (as real units do); the backend stores it. Production path: Amazon Location Service routes + learned dwell times.

Meeting the < 5 s Target

Budget: message sent → visible in browser

  • IoT → queue → Lambda → DynamoDB measured per message: ingestLatencyMs
  • First run: p50 9.3 s messages waited ~10 s in SQS; removing the 1 s batching window → 0.3 s
  • Dashboard poll every 2 s → ≤ 2 s
  • Measured on AWS p50 0.83 s · p95 3.26 s · p99 4.18 s (n = 757)

Typical end-to-end ≈ 1.8 s (p50 + avg. 1 s poll). Worst case at p95 ≈ 5.3 s, right at the limit. Watched by an alarm: consumer lag > 30 s for 3 min → email.

Why REST polling and not WebSockets?
Polling already fits the target. WebSockets would need a connection table, connect/disconnect Lambdas and a fan-out path.
Upgrade path: DynamoDB Streams → Lambda → API Gateway WebSocket, once there are many concurrent viewers.

Reliability: Tested by Injecting Faults

Mechanisms

  • Idempotency seq-conditional writes — duplicates and reordering are harmless
  • DLQ IoT rule errors, invalid payloads and exhausted retries → SQS, 14 days
  • Bisect failing batch is split until the bad record is isolated
  • Max age 1 h stale GPS is not retried forever
  • Alarms DLQ not empty · Lambda errors · stream lag · API 5xx → SNS email

Security

  • Device identity X.509 certificate; IoT policy allows only client IDs shipment-simulator-* and only publish to shipments/*/location
  • Least privilege one role per function with exactly the actions it needs — e.g. ingest gets UpdateItem, the API gets GetItem/Scan/Query, nothing else
  • Writes PUT needs an API key tied to a usage plan (5 req/s); key is never bundled in the site
  • Abuse stage throttling 50 req/s, burst 100; CORS allow-list
  • Encryption at rest: DynamoDB, Kinesis, SQS, S3. In transit: TLS everywhere (MQTT 8883, HTTPS)
Shared responsibility
All managed services → AWS patches the hosts; my part is identities, policies and data.
Known gap → production
An API key identifies a client, not a user.
Next step: Cognito user pool + authorizer, and tenant isolation (customer ID from the token, not the query string).

What Breaks First at 100× ?

  • Ingest fine — 1 shard ≈ 17,000 trucks at 30 s; add shards linearly, Lambda follows
  • Writes fine — every shipment is its own partition key, no hot partition
  • Reads first bottleneck: the list API scans the table on every 2 s poll — cost grows with table size × open browser tabs
  • Fix sparse GSI on active shipments (only in-transit items are indexed) + a few seconds of response caching; metrics pre-aggregated by a stream consumer
  • Push DynamoDB Streams → WebSocket API once polling viewers dominate

Deliberate PoC choice: a scan is correct and cheap for ~2,000 items; the fix is known and isolated to the API Lambda.

Trade-offs I Would Defend

  • Streaming Kinesis vs. IoT → Lambda direct. Ordering + replay for $0.36/day. At 40 trucks the shard is the biggest cost — accepted, and destroyed between sessions.
  • Push REST polling vs. WebSocket. Meets < 5 s with 3 fewer moving parts. Push is the upgrade, not the PoC.
  • Data DynamoDB vs. RDS. Key-value access, no idle cost, no connection pool from Lambda.
  • Reads Scan vs. GSI. Simple and correct at PoC size; first thing to change at scale.
  • Auth API key vs. Cognito. Enough to protect writes in a PoC; Cognito for real users and tenants.
  • Hosting S3 + CloudFront vs. Amplify. One stack, one deploy, one teardown.
