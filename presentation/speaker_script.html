PART 1 — Use Case ~1.5 minutes

Slide 1–2 · Opening & Agenda (45 sec)

"Hello, I'm David Fellner. My project is Tracelane, a fully serverless AWS pipeline that tracks a truck fleet in real time and predicts arrival times.

The talk follows the evaluation criteria: first the use case, then the architecture with the reasons behind each service, then three Well-Architected pillars: Cost Optimization, and both Security and Reliability, because for this system both matter. Then the live demo on AWS, and at the end what I'd change at scale."

Slide 3 · The Problem (45 sec)

"The use case from my 1-pager: a road-freight carrier can't tell its customers where a shipment is right now. Tracking runs on spreadsheets and phone calls, and 'where is my truck?' means calling the driver.

There are three users. The operator, the dispatcher, needs a live view of the fleet and the exceptions. The customer who booked the transport wants their own shipments and reports. And the consignee just wants a link that says when the truck arrives. For the proof of concept I simulate a carrier with 40 trucks on 156 real road lanes; each truck reports every 30 seconds."
PART 2 — Architecture Design ~6 minutes

Slide 4 · Architecture (1.5 min)

"Top row is the write path. Each truck sends its position over MQTT to IoT Core; the connection is authenticated with an X.509 certificate. An IoT rule puts every message into an SQS queue. A Lambda reads the queue in batches of up to 10 and writes the current state and the milestone history into two DynamoDB tables.

Bottom row is the read path. The dashboard is a static React app on S3 behind CloudFront. It reads through API Gateway and a second Lambda, and a third Lambda handles the operator's status update.

Around it: a dead-letter queue for bad messages, CloudWatch alarms that email me, X-Ray tracing and a budget. All of it is one CDK stack."

Slide 5 · Why these services? (2 min)

"For each service I considered an alternative.
IoT Core instead of plain HTTPS to API Gateway: a device keeps one MQTT session open and authenticates with a certificate, instead of an API secret and one HTTP request per ping.
SQS as the buffer between IoT and Lambda; the next slide is about that decision.
Lambda instead of EC2 or Fargate: the work comes in short bursts, so I don't want to pay for a server that is idle most of the time.
DynamoDB instead of RDS: I only ever read by shipment ID, or by shipment ID plus time for the timeline. That's key-value access, with no idle cost and no connection pool to manage from Lambda.
API Gateway instead of a Lambda function URL, because I need API keys, usage plans and throttling for the write endpoint.
S3 and CloudFront instead of Amplify, which I had in the 1-pager: both work, but this way the website is in the same CDK stack and is deployed and destroyed with everything else."

Slide 6 · Why a queue, and why SQS (1.5 min)

"Why a queue at all? IoT rules can invoke Lambda directly. But on AWS I saw why the buffer matters: the 30-day backfill pushed 4,660 messages a minute, and this new account allows only 10 concurrent Lambdas. 2,515 deliveries were throttled. Without a queue those messages would be gone; with SQS they just waited and were redelivered. Zero lost, zero errors.

Why SQS and not Kinesis, which I proposed in the 1-pager? The Free plan doesn't include Kinesis, so I made it a switch in the stack. Comparing them honestly: Kinesis costs 43 cents a day per shard even when idle; SQS costs nothing idle. Kinesis keeps order per truck, but I don't need order, because my sequence-number check makes the result order-independent, and I tested that. What I really lose is replay: with Kinesis I could re-process the last 24 hours after a bad deploy. So: SQS for this workload, Kinesis once I need replay or a second consumer. The Lambda is the same, it's one CDK flag."

Slide 7 · Duplicates and reordering are harmless (1 min)

"MQTT and SQS both deliver at least once, so duplicates happen, and a standard queue doesn't keep order. So every message carries a per-shipment sequence number and DynamoDB only accepts a newer one: a conditional write. The effect is exactly-once, even though delivery isn't. Invalid messages go straight to the dead-letter queue and are never retried; a transient error returns only that one message to the queue."
PART 3 — Well-Architected Pillars ~5 minutes, graded: take your time

Slide 8 · Pillar 1: Cost Optimization (2 min)

"First pillar, Cost Optimization. I went through the cost rules from the first lab one by one.

Turn off services when not in use: nothing in my stack is billed per hour. No server, no database instance, no Kinesis shard. When no truck sends anything, it costs practically nothing, and after the course one command, cdk destroy, removes everything.

Choose size and type wisely: the Lambdas run on ARM, which is cheaper per second, DynamoDB is on-demand so I pay per write instead of reserving capacity, and I chose SQS over Kinesis, because a Kinesis shard is billed every hour, even when idle.

Keep an eye on it: Cost Explorer has no data yet on a new account, so I take the usage from CloudWatch, messages and read and write units, and multiply by the Frankfurt list prices.

Budgets and alerts: two budgets, one for the stack and one for the whole account, which email me at 50 and 80 percent and when the forecast passes 100.

And one lesson: the dashboard reads cost more than the whole pipeline, because every poll scans the table. That's also my answer to what breaks first at scale."

Slide 9 · Pillar 2: Security (1.5 min)

"Second pillar, Security. Devices authenticate with an X.509 certificate, and the IoT policy only allows our client IDs and only publishing to the location topics. Every Lambda has its own role with exactly the actions it needs. Writes need an API key with a usage plan, and everything is encrypted at rest and in transit. Two known gaps. First, in the proof of concept the simulator is one device with one certificate for all 40 trucks. In production every truck would be an IoT Thing with its own certificate, registered through fleet provisioning, so a single stolen truck can be blocked on its own. Second, an API key is not a user identity; in production I'd add Cognito."

Slide 10 · Pillar 3: Reliability (1.5 min)

"Third pillar, Reliability. For a tracking system it matters as much as security: a lost position is a wrong ETA. I tested it like a chaos experiment: replay the same messages with 20 % duplicates, 2 % malformed and reordered. Hypothesis: same final state. Result: 302 of 302 shipments identical, all 58 bad messages in the DLQ. The experiment also found two real bugs, which I fixed.

And AWS gave me two real faults for free. KMS returned a 500 on one DynamoDB write: the Lambda reported that one message as failed, SQS redelivered it, the alarm emailed me. And the 10-Lambda limit throttled 2,515 deliveries; the queue held them all. The dead-letter queue stayed empty both times."

PART 5 — Reflection & Summary ~2.5 minutes

Slide 12 · What breaks first at scale? (1 min)

"If the fleet grew a hundred times: ingest is fine, SQS has no practical throughput limit and Lambda adds queue readers on its own. The real ceiling there is the account's concurrency limit; mine is 10, and I've seen it throttle, without losing anything. Writes are fine, because every shipment is its own partition key.

The first thing to break is reads: the list API scans the whole table on every dashboard poll, and the reads already outweigh the writes today. The fix is known and isolated: a sparse index on active shipments, a few seconds of caching, metrics computed in the write path, and later push over WebSockets. For 2,200 items a scan is correct and cheap, so I kept it simple."

Slide 13 · Trade-offs (30 sec)

"Every choice on this slide has a simpler option and a production option. I took the simple one where it's enough for this use case, and I know what I'd change first: SQS instead of Kinesis until I need replay, polling instead of WebSockets, DynamoDB instead of RDS, a scan instead of an index, an API key instead of Cognito, and S3 with CloudFront instead of Amplify."

Slide 14 · Evaluation criteria, answered (30 sec)

"To close the loop with how the project is evaluated, here's where each question was answered. Architecture: the data flow, how each message is processed, and what breaks first at scale. Why each service and what the alternative was: slide 5, SQS versus Kinesis in detail on slide 6, and the trade-offs. Cost Optimization together with the cost-management rules from the first lab. Instead of choosing one, both Security and Reliability. And the demo."

Slide 15 · Summary (30 sec)

"To sum up: Tracelane is a fully serverless pipeline, IoT Core, SQS, Lambda and DynamoDB, served through API Gateway and CloudFront, all in one CDK stack. For every service I've shown why I chose it and what the alternative was. All three pillars are covered: Cost Optimization with pay-per-use and budgets, Security with certificate auth and least privilege, and Reliability, where no message was lost, neither under injected faults nor under real throttling. Next steps would be Cognito with tenants, an index instead of the scan, WebSocket push, and Kinesis once replay matters. Thank you, I'm happy to take questions."
PART 6 — Q&A Preparation 5–10 minutes
Why SQS and not Kinesis, as in your 1-pager?
The Free plan doesn't include Kinesis, so I made ingestion switchable (-c ingest=sqs) instead of rewriting it; the same Lambda handles both. For this workload SQS is also the cheaper fit: no idle cost (a shard is $0.018/h = $0.43/day in Frankfurt), retries and a DLQ built in. Ordering isn't needed, because the seq-conditioned write gives the same final state in any order (tested with reordering). What I lose is 24 h replay and a second consumer on the same data; that's when I'd switch to Kinesis.
The course asked for Security OR Reliability. Why both?
The 1-pager promised Cost + Security, so Security is the graded one. But for a tracking system reliability is the core property: a lost or duplicated position means a wrong ETA and a wrong on-time rate. So I didn't just list mechanisms, I tested them: 302/302 under injected faults, and two real faults on AWS (KMS 500, 2,515 throttles) with nothing lost.
Why not let the IoT rule call Lambda directly?
No buffer. On this account only 10 Lambdas may run at once; 2,515 deliveries were throttled during the backfill. With SQS they waited and were redelivered, 0 lost. Directly invoked, IoT would retry briefly and then drop them.
How are the dashboard KPIs calculated?
The api Lambda scans the Shipments table on GET /metrics and aggregates shipments delivered in the last 30 (simulated) days. On time: deliveredAt ≤ plannedDeliveryAt. ETA accuracy: mean |delivery − ETA stored at half-way|. CO₂e intensity: Σ CO₂e ÷ Σ km × tonnes. All formulas in docs/METRICS.md.
Where is the ETA calculated?
On the telematics unit (the simulator), like real telematics boxes that know the driver's hours. The backend validates and stores it, and records the ETA at half-way to measure accuracy. Production: Amazon Location Service for routes.
What happens if the Lambda crashes or has a bug?
Transient errors: the Lambda reports only the failed message (partial batch failure), it becomes visible in the queue again after the 180 s visibility timeout and is retried. After 4 failed receives it goes to the DLQ. Poison messages go to the DLQ immediately. A deployed bug: fix it and replay the DLQ. What SQS can't do is replay messages that were processed wrongly; that's the case for Kinesis.
Could this scale to 10,000 trucks?
Ingest yes: SQS has no practical throughput limit and Lambda scales its queue readers up to 1,250 in parallel; I'd raise the account concurrency quota (10 now, 1,000 default). Writes yes: one partition key per shipment. Reads no, not as is: the list API scans the table on each poll. Fix: sparse GSI on active shipments, short caching, and push via DynamoDB Streams → WebSocket.
Why polling and not WebSockets?
Polling every 2 s is fast enough for a dispatcher watching a map. WebSockets need a connection table, connect/disconnect handlers and fan-out. That's the upgrade once there are many concurrent viewers.
How do you register a new truck?
In the PoC the simulator is one device with one certificate (scripts/provision_device.py) that sends for all 40 trucks; the trucks themselves are defined in a catalog file (shared/catalog.json), so there is no registration step. In production each truck would be an IoT Thing with its own certificate, registered automatically on first connect through IoT Core fleet provisioning. A policy variable on the thing name then restricts each truck to its own topic, and a single stolen truck can be blocked without affecting the others.
How do you stop one customer seeing another's shipments?
In the PoC the customer filter is a query parameter, so not secure. Production: Cognito, customer ID taken from the token in the Lambda, never from the request. That's one of the known gaps on my Security slide.
Why DynamoDB and not RDS or Timestream?
Access is by key: current state by shipment ID, timeline by shipment ID + time (sort key). No joins, no idle cost, no connection pool from Lambda. Timestream would suit raw GPS analytics; I only keep milestones.
How do you know the cost before the bill?
CloudWatch usage metrics (messages, read/write units, Lambda GB-seconds) × Frankfurt list prices; Cost Explorer has no data yet on a new account. Two budgets with email alerts ($10 stack budget, $100 account budget). Nothing is billed per hour; cost scales with messages and with open dashboards.
How long was it running, and what did it cost?
Two AWS runs: the first with 29k messages (≈ $0.25 at list prices), the current deployment since 19 Oct with 48k messages so far (≈ $0.65, two-thirds of it dashboard reads). Billed: $0, covered by the Free plan credits.
How did you test it?
Four levels. 24 automated tests run in GitHub Actions on every push: the three Lambdas against mocked DynamoDB and SQS (moto), fed with telemetry from the real simulator; CDK assertion tests for the security properties (API key on PUT, encryption, least-privilege IoT policy); and a test that the in-browser demo mode computes exactly the same KPIs as the deployed API. Then the fault-injection experiment (302/302), and finally the live runs on AWS.
What would you do differently?
Measure on AWS earlier. Design the read path (GSI) together with the write path, not after. And move auth to Cognito from the start, because retrofitting tenancy is harder than building it in.
