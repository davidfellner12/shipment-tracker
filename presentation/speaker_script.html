PART 1 — Use Case & Architecture ~13 minutes

Slide 1–2 · Opening & Problem (1.5 min)

"Hello, I'm David Fellner. My project is Tracelane, a fully serverless AWS pipeline that tracks a truck fleet in real time and predicts arrival times.

The problem from my 1-pager: carriers cannot tell their customers where a shipment is right now. Tracking runs on spreadsheets and phone calls, and about 60 % of customer calls are simply 'where is my order?'. Each of these numbers maps to one feature: a live map with a realistic ETA, a full timeline with proof of delivery, and a public tracking page the customer can open instead of calling."

Slide 3 · Promise → Delivered (1 min)

"In April I made concrete promises: this architecture, under 5 seconds latency, under 5 dollars for the whole PoC, a live status update, and two Well-Architected pillars. This slide is the scorecard. Latency measured on AWS over 757 live messages: median 0.8 seconds, p95 3.3 seconds. Total cost of the AWS run: about 25 cents. One change: I host on S3 and CloudFront instead of Amplify, and I'll explain why."

Slide 4–5 · Architecture & service choices (3 min)

"A simulator drives 40 trucks on 156 real European road lanes. Telemetry goes over MQTT to IoT Core, which authenticates with an X.509 certificate. An IoT rule writes every message into Kinesis, partitioned by shipment. A Lambda consumes the stream and writes the current state and the milestone history to DynamoDB. The dashboard is a static React app on S3 behind CloudFront and reads through API Gateway and a second Lambda.

For each service I considered an alternative.
IoT Core instead of plain HTTPS to API Gateway: trucks keep one MQTT session open and each one has its own certificate, instead of a shared secret and one HTTP request per ping.
Kinesis instead of SQS, for ordering and replay; I'll come back to that on the next slide.
Lambda instead of EC2 or Fargate: the work comes in short bursts, so I don't want to pay for a server that is idle most of the time.
DynamoDB instead of RDS: I only ever read by shipment ID, or by shipment ID plus time for the timeline. That's key-value access, with no idle cost and no connection pool to manage from Lambda.
API Gateway instead of a Lambda function URL, because I need API keys, usage plans and throttling for the write endpoint.
S3 and CloudFront instead of Amplify, which I had in the 1-pager: both work, but this way the website is in the same CDK stack and is deployed and destroyed with everything else.
And an SQS dead-letter queue, because just logging errors would lose the message; in the DLQ I can inspect it and replay it."

Slide 6 · Why Kinesis (1 min)

"Kinesis is the one service I could have left out, because IoT rules can call Lambda directly. I kept it for three reasons: one truck's pings stay in order, 24 hours of replay if a Lambda has a bug, and a buffer for bursts. The price is one provisioned shard, 36 cents a day, the biggest line item of the whole PoC. From the measured message size of 1.76 KB, one shard handles about 17,000 trucks.

One honest note: my AWS account is on the Free plan, which doesn't include Kinesis. So the stack has a switch, and for the measured run I deployed it with SQS in Kinesis's place, feeding the same Lambda. I lose ordering, which my sequence-number check already makes irrelevant, and replay, which is the real reason Kinesis is the production design."

Slide 7 · Idempotent ingestion (1 min)

"MQTT QoS 1 and Kinesis retries both deliver duplicates, and the network reorders. So every message carries a per-shipment sequence number and DynamoDB only accepts a newer one: a conditional write. Invalid messages go straight to a dead-letter queue and are never retried; transient errors retry only from the failed record."

Slide 8 · ETA (1 min)

"EU drivers must take a 45-minute break after 4.5 hours and an 11-hour rest after 9. Distance divided by speed ignores that and is off by 220 minutes on average early in the trip. With the driving-time rules it's 27, eight times better. Honest caveat: the predictor shares rules with the simulator, so this is an upper bound."

Slides 9–12 · Pillars (4 min, graded: take your time here)

Latency (slide 9)

"The target was under 5 seconds from the truck to the screen. The Lambda stamps every message with how long it took from the truck to DynamoDB. On AWS that's 0.83 seconds at the median and 3.3 at p95. On top of that comes the dashboard poll, every 2 seconds, so a typical update is on screen in about 2 seconds. My first run was at 9 seconds: messages were waiting in the queue because of a 1-second batching window. Removing it brought the waiting time down to 0.3 seconds. An alarm emails me if the pipeline falls more than 30 seconds behind.
Why polling and not WebSockets? Polling already meets the target, and WebSockets would add a connection table, two more Lambdas and a fan-out path."

Reliability (slide 10)

"I tested reliability like a chaos experiment: replay the same messages with 20 % duplicates, 2 % malformed and reordered. Hypothesis: same final state. Result: 302 of 302 shipments identical, all 58 bad messages in the DLQ. The experiment also found two real bugs, which I fixed.

And on the live AWS run I got a real fault for free: AWS KMS returned a 500 on one DynamoDB write. The Lambda reported just that message as failed, SQS redelivered it, the lag alarm emailed me, and the dead-letter queue stayed empty. Nothing was lost."

Security (slide 11)

"The device policy only allows our client IDs and only publishing to the location topics. Every Lambda has its own role with exactly the DynamoDB actions it needs. Writes need an API key with a usage plan; everything is encrypted at rest and in transit. Known gap: an API key is not a user identity. In production I'd add Cognito."

Cost (slide 12)

"Everything is pay-per-use except the Kinesis shard. Lambdas run on Graviton, data expires via TTL, logs after two weeks, a Budget emails me at 50, 80 and 100 %. With Kinesis I'd destroy the stack after every session; with SQS the idle stack costs cents, so I left it up for today. One thing I learned from the cost model: an open dashboard tab costs more than the pipeline, because each poll scans the table. That's also my answer to what breaks first at scale."

Back to the slides: 13 · What breaks first at 100× (1 min)

"If the fleet grew a hundred times, ingest is fine: one shard carries about 17,000 trucks and you add shards linearly. Writes are fine, because every shipment is its own partition key. The first thing to break is reads: the list API scans the table on every 2-second poll, so cost grows with table size times open tabs. The fix is known and isolated: a sparse index on active shipments, a few seconds of caching, and later push over WebSockets. For 2,000 items a scan is correct and cheap, so I kept it simple."

15 · Trade-offs I would defend (30 sec)

"Every choice on this slide has a cheaper or simpler option and a production option. PART 3 — Q&A Preparation 5 minutes
Why Kinesis and not SQS?
SQS deletes a message once it's consumed and only orders in FIFO mode, which caps throughput. Kinesis keeps order per partition key (= shipment) and lets me replay 24 hours. Cost: 1 provisioned shard ≈ $0.36/day.
But your live run used SQS. Doesn't that contradict the design?
The Free plan doesn't include Kinesis, so I made ingestion switchable (-c ingest=sqs) instead of rewriting it. The same Lambda handles both. Ordering isn't needed, because the seq-conditioned write gives the same final state in any order (tested with reordering). What SQS can't do is replay 24 h after a bad deploy, and that's why production stays on Kinesis.
Why provisioned and not On-Demand Kinesis?
On-Demand has a higher per-hour base price per stream. At 40 trucks one shard has > 99 % headroom, so provisioned is cheaper. On-Demand is right when traffic is unpredictable and large.
Where is the ETA calculated?
On the telematics unit (the simulator), like real telematics boxes that know the driver's hours. The backend validates and stores it, and records the ETA at half-way to measure accuracy. Production: Amazon Location Service for routes.
What happens if the Lambda crashes or has a bug?
Transient errors: the batch reports the failed record, Lambda retries from there (3×, batch is bisected). Poison messages: straight to the DLQ. A deployed bug: fix it and Kinesis still holds 24 h of data to replay. Messages older than 1 h are not retried; stale GPS is useless.
Could this scale to 10,000 trucks?
Ingest yes: ~17,000 trucks per shard at 30 s, add shards, one Lambda per shard. Writes yes: one partition key per shipment. Reads no, not as is: the list API scans the table on each poll. Fix: sparse GSI on active shipments, short caching, and push via DynamoDB Streams → WebSocket.
Why polling and not WebSockets?
Polling every 2 s already meets the 5 s target. WebSockets need a connection table, connect/disconnect handlers and fan-out. That's the upgrade once there are many concurrent viewers.
How do you stop one customer seeing another's shipments?
In the PoC the customer filter is a query parameter, so not secure. Production: Cognito, customer ID taken from the token in the Lambda, never from the request. That's on my "Known gap" slide.
Why DynamoDB and not RDS or Timestream?
Access is by key: current state by shipment ID, timeline by shipment ID + time (sort key). No joins, no idle cost, no connection pool from Lambda. Timestream would suit raw GPS analytics; I only keep milestones.
How do you know the cost before the bill?
Per-day model on the cost slide, the Budget alerts, and Cost Explorer. The one fixed cost is the shard; everything else scales with messages and with open dashboards.
How did you test it?
Four levels. 24 automated tests run in GitHub Actions on every push: the three Lambdas against mocked DynamoDB and SQS (moto), fed with telemetry from the real simulator; CDK assertion tests for the security properties (API key on PUT, encryption, least-privilege IoT policy); and a test that the in-browser demo mode computes exactly the same KPIs as the deployed API. Then the fault-injection experiment (302/302), and finally the live run on AWS with measured latency and cost.
What would you do differently?
Measure on AWS earlier. Design the read path (GSI) together with the write path, not after. And move auth to Cognito from the start, because retrofitting tenancy is harder than building it in.
