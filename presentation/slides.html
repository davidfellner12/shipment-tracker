1 · Use case

The Problem

Carriers can't tell customers where a shipment is right now.

Operator

Customer
own shipments + reports
Consignee
tracking link, no login

PoC: 40 trucks · 156 real road lanes · position every 30 s

The use case from my 1-pager: a road-freight carrier can't tell its customers where a shipment is right now. Tracking runs on spreadsheets and phone calls, and "where is my truck?" means calling the driver.

There are three users. The operator, the dispatcher, needs a live view of the fleet and the exceptions. The customer who booked the transport wants their own shipments and reports. And the consignee just wants a link that says when the truck arrives.

For the proof of concept I simulate a carrier with 40 trucks on 156 real road lanes; each truck reports every 30 seconds.

Top row is the write path. Each truck sends its position over MQTT to IoT Core; the connection is authenticated with an X.509 certificate. An IoT rule puts every message into an SQS queue. A Lambda reads the queue in batches of up to 10 and writes the current state and the milestone history into two DynamoDB tables.

Bottom row is the read path. The dashboard is a static React app on S3 behind CloudFront. It reads through API Gateway and a second Lambda, and a third Lambda handles the operator's status update.

Around it: a dead-letter queue for bad messages, CloudWatch alarms that email me, X-Ray tracing and a budget. All of it is one CDK stack.

For each service I considered an alternative.

IoT Core instead of plain HTTPS to API Gateway: a device keeps one MQTT session open and authenticates with a certificate, instead of an API secret and one HTTP request per ping.

SQS as the buffer between IoT and Lambda; the next slide is about that decision.

Lambda instead of EC2 or Fargate: the work comes in short bursts, so I don't want to pay for a server that is idle most of the time.

DynamoDB instead of RDS: I only ever read by shipment ID, or by shipment ID plus time for the timeline. That's key-value access, with no idle cost and no connection pool to manage from Lambda.

API Gateway instead of a Lambda function URL, because I need API keys, usage plans and throttling for the write endpoint.

S3 and CloudFront instead of Amplify, which I had in the 1-pager: both work, but this way the website is in the same CDK stack and is deployed and destroyed with everything else.

Why a queue at all? IoT rules can invoke Lambda directly. But on AWS I saw why the buffer matters: the 30-day backfill pushed 4,660 messages a minute, and this new account allows only 10 concurrent Lambdas. 2,515 deliveries were throttled. Without a queue those messages would be gone; with SQS they just waited and were redelivered. Zero lost, zero errors.

Why SQS and not Kinesis, which I proposed in the 1-pager? The Free plan doesn't include Kinesis, so I made it a switch in the stack. Comparing them honestly: Kinesis costs 43 cents a day per shard even when idle; SQS costs nothing idle. Kinesis keeps order per truck, but I don't need order, because my sequence-number check makes the result order-independent, and I tested that. What I really lose is replay: with Kinesis I could re-process the last 24 hours after a bad deploy. So: SQS for this workload, Kinesis once I need replay or a second consumer. The Lambda is the same, it's one CDK flag.

2 · Architecture design · ingestion

Duplicates and Reordering Are Harmless

table.update_item(
  ...,
  ConditionExpression=
    "attribute_not_exists(seq) OR seq < :newseq",
)
# duplicate / older message → skipped
  • Invalid → DLQ, never retried
  • Duplicate / old → skipped
  • Transient error → only that message retried

MQTT and SQS both deliver at least once, so duplicates happen, and a standard queue doesn't keep order. So every message carries a per-shipment sequence number and DynamoDB only accepts a newer one: a conditional write. The effect is exactly-once, even though delivery isn't. Invalid messages go straight to the dead-letter queue and are never retried; a transient error returns only that one message to the queue.

3 · Well-Architected · pillar 1

Cost Optimization

Keep an eye on itCloudWatch usage × list price

  • Lesson dashboard reads cost more than the pipeline

First pillar, Cost Optimization. I went through the cost rules from the first lab one by one.

Turn off services when not in use: nothing in my stack is billed per hour. No server, no database instance, no Kinesis shard. When no truck sends anything, it costs practically nothing, and after the course one command, cdk destroy, removes everything.

Choose size and type wisely: the Lambdas run on ARM, which is cheaper per second, DynamoDB is on-demand so I pay per write instead of reserving capacity, and I chose SQS over Kinesis, because a Kinesis shard is billed every hour, even when idle.

Keep an eye on it: Cost Explorer has no data yet on a new account, so I take the usage from CloudWatch, messages and read and write units, and multiply by the Frankfurt list prices.

Budgets and alerts: two budgets, one for the stack and one for the whole account, which email me at 50 and 80 percent and when the forecast passes 100.

And one lesson: the dashboard reads cost more than the whole pipeline, because every poll scans the table. That's also my answer to what breaks first at scale.

3 · Well-Architected · pillar 2

Security

  • Devices X.509 certificate, publish to location topics only
  • IAM one role per Lambda, only the actions it needs
  • Writes API key + usage plan
  • Abuse throttling · CORS · schema validation
  • Encryption at rest + TLS in transit
Known gap
1 certificate for the whole fleet → 1 per truck in production
Known gap
API key ≠ user identity → Cognito in production

Second pillar, Security. Devices authenticate with an X.509 certificate, and the IoT policy only allows our client IDs and only publishing to the location topics. Every Lambda has its own role with exactly the actions it needs. Writes need an API key with a usage plan, and everything is encrypted at rest and in transit. Two known gaps. First, in the proof of concept the simulator is one device with one certificate for all 40 trucks. In production every truck would be an IoT Thing with its own certificate, registered through fleet provisioning, so a single stolen truck can be blocked on its own. Second, an API key is not a user identity; in production I'd add Cognito.

Third pillar, Reliability. For a tracking system it matters as much as security: a lost position is a wrong ETA. I tested it like a chaos experiment: replay the same messages with 20 % duplicates, 2 % malformed and reordered. Hypothesis: same final state. Result: 302 of 302 shipments identical, all 58 bad messages in the DLQ. The experiment also found two real bugs, which I fixed.

And AWS gave me two real faults for free. KMS returned a 500 on one DynamoDB write: the Lambda reported that one message as failed, SQS redelivered it, the alarm emailed me. And the 10-Lambda limit throttled 2,515 deliveries; the queue held them all. The dead-letter queue stayed empty both times.

5 · Reflection

What Breaks First at Scale?

  • Ingest fine — SQS scales, Lambda follows
  • Writes fine — one partition key per shipment
  • Concurrency account limit: 10 here, 1,000 default
  • Reads table scan on every poll — first bottleneck
  • Fix index + cache + push

If the fleet grew a hundred times: ingest is fine, SQS has no practical throughput limit and Lambda adds queue readers on its own. The real ceiling there is the account's concurrency limit; mine is 10, and I've seen it throttle, without losing anything. Writes are fine, because every shipment is its own partition key.

The first thing to break is reads: the list API scans the whole table on every dashboard poll, and the reads already outweigh the writes today. The fix is known and isolated: a sparse index on active shipments, a few seconds of caching, metrics computed in the write path, and later push over WebSockets. For 2,200 items a scan is correct and cheap, so I kept it simple.
